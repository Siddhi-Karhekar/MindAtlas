# Deploying Mind Atlas

**What is live:** two free **Render** services that auto-deploy from `main`,
and a free **MongoDB Atlas** database.

| Piece | Where | URL |
| --- | --- | --- |
| Client (React, static files) | Render **Static Site** `mindatlas`, root `client/` | https://mindatlas.onrender.com |
| API (Express) | Render **Web Service** `mindatlas-api`, root `server/` | https://mindatlas-api.onrender.com |
| Database | MongoDB Atlas **M0**, AWS Mumbai (`ap-south-1`), database `mindatlas` | — |

The browser loads the site from `mindatlas.onrender.com` and calls the API on
`mindatlas-api.onrender.com`, so the API must allow that origin (`CORS_ORIGIN`).
`render.yaml` is the written record of both services' settings.

Why this setup: Render runs a normal long-lived Node server, which OCR
(tesseract.js), PDF parsing and the in-memory rate limiter need; serverless
functions (Vercel, Netlify) are a poor fit. Atlas is required because Render's
disk is wiped on every restart, redeploy and wake-up. Total cost: ₹0.

---

## 1. Database: MongoDB Atlas (~10 min)

1. https://cloud.mongodb.com → **Create** → **M0 Free**, AWS **Mumbai (ap-south-1)**.
   Untick "Preload sample dataset" (it eats the 512 MB quota).
2. **Security → Database Access → Add New Database User**: password auth,
   role **Read and write to any database** (not Atlas Admin). Use an
   autogenerated password: letters and digits only, so it needs no escaping.
3. **Security → Network Access → Add IP Address → Allow access from anywhere**
   (`0.0.0.0/0`). Render's free tier has no fixed outgoing IP.
4. **Clusters → Connect → Drivers** → copy the string and put the password in
   place of `<db_password>`, **removing the `<` `>` too**:
   `mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/?appName=Cluster0`.
   The app always uses the database `mindatlas`; no need to add a name.

## 2. API: Render Web Service (~5 min + build)

**New + → Web Service →** the `Siddhi-Karhekar/MindAtlas` repo.

| Setting | Value |
| --- | --- |
| Name | `mindatlas-api` |
| Region | Singapore (closest to the Mumbai database) |
| Branch / Root Directory | `main` / `server` |
| Build / Start Command | `npm ci` / `npm start` |
| Health Check Path | `/api/health` |
| Instance type | Free |

Environment (**spell the keys exactly**; see "Environment variables" below):
`NODE_ENV=production`, `NODE_VERSION=22`, `TRUST_PROXY=1`, `MONGODB_URI`,
`JWT_SECRET`, `CORS_ORIGIN` (after step 3), optional `GROQ_API_KEY`.

When it is live the **Logs** show `[db] connected to MongoDB` and
`[server] listening on :10000`, and `/api/health` returns `{"ok":true}`.

## 3. Client: Render Static Site (~3 min)

**New + → Static Site →** the same repo.

| Setting | Value |
| --- | --- |
| Name | `mindatlas` |
| Branch / Root Directory | `main` / `client` |
| Build Command | `npm ci && npm run build` |
| Publish Directory | `dist` |
| Environment | `VITE_API_BASE=https://mindatlas-api.onrender.com/api` |

Then **Redirects/Rewrites → Add Rule**: source `/*`, destination
`/index.html`, action **Rewrite**. Without it, refreshing any page except the
home page is "Not Found".

## 4. Connect the two

On `mindatlas-api` → **Environment**: `CORS_ORIGIN=https://mindatlas.onrender.com`
(exact origin, no trailing `/`) → **Save, rebuild, and deploy**. Then sign up
on the site; within a minute Atlas → Browse Collections shows the `mindatlas`
database with a `users` collection.

## Environment variables

**API (`mindatlas-api`)** — `server/.env.example` documents each one.

| Key | Value | Notes |
| --- | --- | --- |
| `NODE_ENV` | `production` | Enforces a strong `JWT_SECRET`, blocks CORS unless `CORS_ORIGIN` is set, and **refuses to start without `MONGODB_URI`** |
| `MONGODB_URI` | Atlas string | Without it the app would use a local file that Render wipes. A misspelling (we once had `MONDODB_URI`) now fails the deploy and names the near-miss |
| `JWT_SECRET` | 32+ random chars | `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
| `CORS_ORIGIN` | `https://mindatlas.onrender.com` | Comma-separate several origins if needed |
| `TRUST_PROXY` | `1` | So rate limits see each user's IP, not Render's proxy |
| `NODE_VERSION` | `22` | |
| `GROQ_API_KEY` | optional | https://console.groq.com/keys - without it, questions and grading use the rule-based fallback |

**Client (`mindatlas`)**: `VITE_API_BASE=https://mindatlas-api.onrender.com/api`.
It is baked in when the site is built: if the API URL changes, change it
here and **Manual Deploy → Deploy latest commit**.

Never commit these values. `.env` files are git-ignored and CI runs
`gitleaks` over the whole history.

## Backups (Atlas M0 has none)

Take one before anything that rewrites data on the live site (e.g. the graph
relink tool), and before demos.

1. Once: add the live string to `server/.env` as **`ATLAS_URI=`** (not
   `MONGODB_URI` - that would point your local dev server at the live data).
2. `cd server && npm run db:backup` → writes
   `server/backups/mindatlas-<UTC time>/` (one JSON file per collection plus a
   `manifest.json` with counts). The folder is git-ignored: it contains every
   student's data - keep it private, never commit or share it.
3. To put a backup back: `npm run db:restore -- backups/mindatlas-<time>`
   shows what would change; add `--yes` to do it. Each collection in the
   backup is emptied and refilled. Set `RESTORE_URI=...` to restore somewhere
   other than `ATLAS_URI` (e.g. a local test database) - practise there first.

## Keeping it awake (uptime pinger)

The free API sleeps after 15 idle minutes; the next request waits ~20–50 s.
Before demos, keep it warm with a free monitor:

1. Sign up at https://uptimerobot.com (free plan).
2. **New monitor → HTTP(s)**, URL `https://mindatlas-api.onrender.com/api/health`,
   interval **5 minutes**.
3. Pause it after the demo if you like: Render's free plan includes 750
   instance-hours a month, enough for one service running non-stop.

The static site never sleeps.

## Rotating secrets

| Secret | How | Effect |
| --- | --- | --- |
| `JWT_SECRET` | New value in Render → Environment → save and deploy | Everyone is signed out once |
| Atlas password | Atlas → Database Access → Edit → new password; update `MONGODB_URI` on Render **and** `ATLAS_URI` locally | Brief outage until the API redeploys |
| `GROQ_API_KEY` | Revoke at console.groq.com, add the new one on Render | None |

Rotate immediately if a value ever appears in a screenshot, chat or commit.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Deploy fails: `MONGODB_URI is not set, and NODE_ENV=production` | The variable is missing or misspelled on `mindatlas-api` - the message lists similar names |
| Logs: `bad auth : authentication failed` | Wrong password in the string, or the `<` `>` placeholder brackets are still there |
| Logs: `MongoServerSelectionError` | Atlas Network Access lacks `0.0.0.0/0` |
| Logs: `JWT_SECRET must be at least 32 characters` | Set a longer secret |
| Site says "Failed to fetch" | `CORS_ORIGIN` not exactly `https://mindatlas.onrender.com`, or the API is still waking up |
| Refreshing a page gives "Not Found" | The static site's `/*` → `/index.html` rewrite rule is missing |
| First photo upload after waking is slow | tesseract downloads its language model once per wake-up |

## Rebuilding from this Blueprint

`render.yaml` recreates both services: **New + → Blueprint → this repo**. Use
it for a fresh workspace, or after deleting the old services. Applying it next
to the existing services would clash on their names. It asks for
`MONGODB_URI` and `GROQ_API_KEY`, and generates a new `JWT_SECRET` (everyone
is signed out once). If Render gives the API a different URL, update
`VITE_API_BASE` and `CORS_ORIGIN` to match.

## Other ways to run it

- **One container** (`Dockerfile` in the repo root): builds the client and
  serves it from the API on one URL, so no CORS is needed. Runs on Railway,
  Fly.io, Koyeb, Cloud Run or any VPS with `NODE_ENV=production`,
  `JWT_SECRET`, `MONGODB_URI`, `TRUST_PROXY=1`. The root `package.json`
  (`npm run build` / `npm start`) does the same without Docker.
- **Locally, like production**: `docker compose up --build`, then
  http://localhost:4000 (that image plus its own MongoDB; never the live one).
